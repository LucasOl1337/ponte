# Ponte lab

The real server with fake desktop tools, for exercising a phone without a live desktop.

```sh
tools/lab/run.sh                                  # HTTP 127.0.0.1:8799, prints the #pair= URL
adb -s SERIAL reverse tcp:8799 tcp:8799           # phone's localhost:8799 → this PC
adb -s SERIAL shell am start -a android.intent.action.VIEW -d 'http://127.0.0.1:8799/#pair=TOKEN'
```

`PONTE_LAB_DIR` (default `.work/lab`) holds `events.jsonl` (every fake call), `clipboard.bin` (the last image the fake `wl-copy` received) and `state.json` (cursor, held button, typed text, fcitx focus). `PONTE_LAB_MONITOR=3440x1440` changes the synthetic monitor; `PONTE_LAB_BACKDROP=image.png` tiles a real screenshot under it so frame sizes look like a real desktop (e.g. `magick docs/assets/desktop-control.png docs/assets/desktop-notifications.png +append .work/backdrop.png`); `PONTE_LAB_ACCEL=2` is the pointer acceleration the fake compositor applies until the server sets the device profile flat, which reproduces the real bug.

The synthetic monitor shows a coordinate grid, targets A/B (text fields: a left click turns the fcitx focus flag on) and C (a button: off), the cursor with its coordinates, the last clicks and whatever was typed.

- `tap-test.py --serial SERIAL` taps at known fractions of the streamed image (found on the device screenshot) and compares with the cursor the server placed. Independent of the page's own numbers.
- `cdp.mjs` needs a debuggable Chrome (`adb forward tcp:9222 localabstract:chrome_devtools_remote`): `rect`, `pinch`, `tap`, `tap-check LABEL`, `drag`, `two-drag`, `text`, `key`, `click SELECTOR`, `eval JS`.
- `bin/claude` and `bin/codex` stand in for the agent CLIs: a session started from Home runs them, and they print the request they got as argv (also logged to `events.jsonl`), then echo each typed line. No model is called.
- On a terminal, `bin/claude` draws a Claude Code-like TUI instead (`bin/_claude_tui.py`): the conversation scrolls in colour (SGR, truecolour orange), the footer (input box, mode line, permission menu) is redrawn in place, the terminal cursor is hidden and bracketed paste is on. Enter sends a request and it asks to run `npm test` with a 1/2/3 menu (1/2/3, arrows + Enter, Esc = 3); Shift+Tab cycles default, accept edits and plan mode; Ctrl+C twice or Ctrl+D exits. Every recognised key (`{"tool":"claude-tui","key":...}`), request, paste and menu answer goes to `events.jsonl`. `PONTE_LAB_CLAUDE=line` keeps the old line-echo fake.
- `fake-agent.sh start|waiting|busy|ready|stop` runs one fake Claude Code (a `sleep` named `claude` plus its session file) that the agent scanner sees go working → waiting or working → ready, for the agent alerts (`/api/agents/events`) without calling a model. `HOME` picks the `~/.claude` it writes to; `stop` removes what it wrote.
- `pinch.py` sends a two-finger gesture through `sendevent` (rooted emulator only).
- Lights: the lab never runs the owner's Magma controller (it drives the real RGB). `PONTE_LAB_MAGMA=<folder with a controller.py copy>` runs that copy through `magma.py` with its state and `telinha` under `$PONTE_LAB_DIR/magma-home`, against the fake `openrgb`, which behaves like 1.0rc3: one missing `--device` aborts the whole call. `PONTE_LAB_OPENRGB_DEVICES` ('|'-separated) is what is on the bus (default: this PC without the sleeping G515 keyboard); `PONTE_LAB_OPENRGB_FAIL` names devices whose write fails; `PONTE_LAB_OPENRGB_DELAY=5` adds the per-call detection time of the real CLI.

- Remote desktop (`/api/rd`): `run.sh` sets `PONTE_RD_CAPTURE=lab` (an ffmpeg `testsrc2` + x264 zerolatency stream instead of the screen) and `PONTE_RD_INPUT=dry-run`: `backend/rd-input.py` never opens `/dev/uinput` and appends each evdev frame it would write to `events.jsonl` (`{"tool":"rd-input","dev":"ponte-rd-keys","events":[["EV_KEY","KEY_A",1]]}`). The fake `wl-paste --watch` follows `clipboard.bin`, so `clip` works both ways. `PONTE_LAB_EXTRA_MONITORS="LAB-2:1280x720"` adds outputs to `hyprctl -j monitors` for the monitor picker (the screenshot fake always draws LAB-1). With `public/rd.html` present, `run.sh` also prints the `rd.html#pair=` URL.
- The lab stream carries its capture time: 44 cells of 16x16 px at the top-left, most significant bit first, white = 1, the wall-clock ms epoch when the frame left ffmpeg's `realtime` filter. `rd-measure.mjs --url ws://127.0.0.1:8799/api/rd --token-file .work/lab/data/token --band` decodes what arrived and reports capture → send and capture → arrival, plus fps, bitrate, keyframe/delta sizes and RTT; `--lab` runs the same in-process, `--gsr DP-3 --seconds 8` measures a real monitor with input off (keep real captures ≤ 10 s), `--switch NAME` times an encoder restart.
- `PONTE_RD_LAB_SCENE=desktop` (or `rd-measure.mjs --scene desktop`) swaps the test pattern for a desktop-like picture: `docs/assets/desktop-control.png` as the backdrop, a terminal scrolling source code, a moving cursor, and a VBV of two seconds. Its keyframes and deltas come out the size gpu-screen-recorder makes them (1080p30 at 2 Mbps: ~100 KB keyframes, ~5 KB deltas; testsrc2 gives ~20 KB keyframes), which is what a slow link feels. The band is painted on top as in the pattern.
- Readable text. `tools/lab/text-backdrop.sh` draws a backdrop of 14 px monospace text at the monitor's size (default 3440x1440, `.work/backdrop-text.png`): small native text like a terminal on the real monitor, which the stretched default backdrop is not. `PONTE_RD_LAB_BACKDROP=FILE` puts it under the desktop scene. `rd-measure.mjs --legible` decodes every fourth frame, scales it back to the monitor (a WAN step sends fewer pixels) and compares a block of still text (22% × 12% of the monitor, at 2%,15%: away from the terminal, the cursor and the band) with the backdrop: PSNR per second in `--timeline` (`db`) and `legible.readableFromS`, the first second from which it stays over `--legible-db N` (default: 1 dB under the best). On the text backdrop at 3440x1440 the phone's JPEG Sharp is 27.7 dB, a 1920 px picture can never pass 21.3 and JPEG Balanced is 20.3: `--legible-db 27` is "as readable as Sharp".
- `rd-link.sh` runs `rd-measure.mjs` over a simulated internet link: a private user + network namespace (`unshare -rn`) with netem on its own loopback, MTU 1280, offloads off. Server → client gets `--netem` (default `delay 12ms loss 1% limit 150`, about 24 ms round trip and a ~190 KB queue at the bottleneck) and a rate that follows `--plan` (`0:2500kbit,20:20mbit` = 2.5 Mbps, then 20 Mbps from second 20; `none` = unlimited); the way back gets 12 ms. It defaults to `--lab --scene desktop --port 8800`. `--client old` sends pings and stats the way the page did up to 0.1.0-alpha.29; `--client new` also announces `caps`/`view` (`--view`, 1920x1080) and acks each arrival at most every 50 ms like the current page. `--timeline` prints one line per second (delivered fps and kbps, rtt, encoder fps/kbps/size/keyint, the rate control's decisions, Node buffer, kernel `notsent`, capture → arrival p95, keyframes), `--trace 14-20` every frame's lateness in that window and `--dump FILE` saves the received H.264. The report adds, after `--warmup` seconds (5), the share of frames over 500 ms, stretches over 500 ms longer than a second and freezes over 250 ms. `RD_LINK_SYSCTL="net.ipv4.tcp_notsent_lowat=131072"` sets per-namespace sysctls for the run. `RD_LINK_BACK_DELAY` (12ms) sets the way back, e.g. `5ms` with `--netem "delay 5ms limit 150"` for a near link that opens as LAN. Nothing outside the namespace changes; `--plan`/`--netem` refuse to run outside it. The scenarios of the WAN work (ADR 0001): M0 `--plan 0:none --netem "delay 0ms" --seconds 30`, M1 `--plan 0:2500kbit --seconds 60`, M2 `--plan 0:20mbit,15:2000kbit,45:20mbit --seconds 60`, M3 `--plan 0:2500kbit --netem "delay 25ms loss 3% limit 400" --seconds 60`, each with `--kbps 12000 --timeline` and both clients.
- The phone's Auto over that link: `RD_LINK_CLIENT=tools/lab/auto-measure.mjs tools/lab/rd-link.sh --plan 0:2500kbit --seconds 60 --timeline` swaps the client for one that plays the page with Auto chosen: the video with acks, JPEG Sharp from `/api/stream`, and `createAutoChooser` read out of `public/app.js` to move between them. Each second gives the link, what is on screen, kbps, the encoder's width and the PSNR of still text against what the picture is made from (the backdrop for the video, the synthetic monitor's PNG for JPEG); the report gives the first readable second, the second from which it stays readable, the readable share and every hand-over. `--video-only` is the page before Auto could pick JPEG, `--start jpeg` opens on JPEG. Use it with `PONTE_RD_LAB_BACKDROP` from `text-backdrop.sh`; the fake grim makes the JPEG side capture-bound (1-2 fps of 3440 px), which the page's link estimate discounts through `X-Capture-Ms`.

- `emu.sh start|flags|sleep|wake|stop|status` runs the Android emulator (AVD `ponte-celular`, unit `ponte-emu`, `emulator-5554`) on the host GPU in the idle CPU class. With Chrome showing this lab's stream at 1344x2992 that is ~0.6-1.1 core, against ~3.6 on `-gpu swiftshader_indirect`; with the screen off (`sleep`, the page hides and the stream stops) ~0.1. On `-gpu host` the guest's hardware video frames come out solid green, so `start` (or `flags` on a running guest) writes `--disable-accelerated-video-decode` for Chrome and WebView: H.264 is decoded in software inside Chrome, so decoder bugs of a real phone's MediaCodec do not show here. `flags` runs `adb root`, which drops that serial's `adb reverse` ports. `PONTE_EMU_AVD|UNIT|PORT|GPU` change the defaults.

`uwsm-app` (the Dev tab's "Abrir no PC") only logs the attach argv and never opens a window; `omarchy-shell lock isLocked` and `omarchy-system-lock` read and set `locked` in the lab's `state.json`, never the real PC's lock.

## Two nodes (mesh)

```sh
node tools/lab/mesh.mjs      # pc-teste on 127.0.0.1:8799, notebook-teste on :8797, each prints its #pair= URL
```

Two real servers in one process, each with its own data, CA (`.work/lab-mesh/a|b/tls`), owner token and fake desktop; the synthetic monitor is titled with the node's name (`PONTE_LAB_TITLE`) and notebook-teste's is 1366x768. Their tailnet TLS listeners sit on 127.0.0.1:8798 and :8796, discovery points each at the other and the whois stand-in says "same owner" for 127.0.0.1, so pairing, the pinned CA and the `?node=` relay run the production code. On pc-teste: Home → Devices → Ask for access; approve the code on notebook-teste's own page; then pick notebook-teste in the selector and open the screen. `PONTE_LAB_MESH_DIR` and `PONTE_LAB_PORT_A|B`, `PONTE_LAB_NATIVE_A|B` move it.

The fleet and the device list (`/api/devices`, `./ponte devices`) see a synthetic network from `tools/lab/net/`, never the machine's real one: a tailnet (`tailscale status --json` with pc-teste, notebook-teste, celular-teste, servidor-teste and an offline tablet-teste on 192.0.2.x), an SSH config whose connections are refused at once, and an adb on pc-teste that sees celular-teste. pc-teste is a `pc` and notebook-teste a `notebook` in the mesh hello.
